# راهنمای جامع استقرار و عملیات کلاستر PostgreSQL HA

این راهنما مسیر استفاده از پروژه برای یک کلاستر سه‌نودی روی Ubuntu 24.04 را
توضیح می‌دهد. PostgreSQL نسخه 16، Patroni، etcd سه‌نودی، HAProxy و Keepalived
روی همان سه سرور اجرا می‌شوند. مقادیر نمونه را با آدرس‌های واقعی سازمان
جایگزین کنید.

## معماری و پیش‌نیاز

- گروه `postgresql_cluster` باید دقیقاً سه میزبان داشته باشد.
- هر میزبان باید `ansible_host` و `node_fqdn` یکتا داشته باشد.
- دیسک داده باید قبل از مقداردهی اولیه خالی و قابل شناسایی باشد؛ مقدار
  `postgres_data_disk_allow_initialize` به‌صورت پیش‌فرض `false` است.
- DNS، زمان، مخزن بسته و مسیر SSH/Ansible باید قبل از اجرا بررسی شوند.
- VIP فقط توسط Keepalived و سرویس PostgreSQL از مسیر HAProxy ارائه می‌شود.

پورت‌های اصلی بین نودها 5432 برای PostgreSQL، 8008 برای REST Patroni، 2379
برای client etcd و 2380 برای peer etcd هستند. دسترسی مستقیم برنامه‌ها باید از
طریق VIP و HAProxy کنترل شود، نه با باز کردن عمومی PostgreSQL.

## آماده‌سازی متغیرها و رمزها

1. `inventory/production/hosts.yml` را با سه نود واقعی تکمیل کنید.
2. `inventory/production/group_vars/all/main.yml` را برای شبکه، VIP، DNS، دیسک
   و CIDRهای بررسی‌شده تنظیم کنید.
3. فایل `inventory/production/group_vars/all/vault.yml` را بسازید و با Ansible
   Vault رمزگذاری کنید. رمزهای `vault_*` را در Git عادی قرار ندهید.

```bash
ansible-vault create inventory/production/group_vars/all/vault.yml
ansible-vault view inventory/production/group_vars/all/vault.yml
```

حداقل رمزهای لازم عبارت‌اند از رمز sudo، superuser، replication، rewind، REST
Patroni و احراز هویت Keepalived. از رمزهای تصادفی و طولانی استفاده کنید؛ مقدار
`CHANGE_ME` توسط preflight رد می‌شود.

## اجرای اولیه کلاستر

قبل از تغییر هر سرویس، فقط preflight را اجرا کنید:

```bash
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/preflight.yml --ask-vault-pass -K
```

سپس استقرار کامل را روی هر سه نود اجرا کنید. از `--limit` استفاده نکنید؛ این
پروژه برای quorum سه‌نودی به حضور همه اعضا نیاز دارد:

```bash
ansible-playbook -i inventory/production/hosts.yml \
  site.yml --ask-vault-pass -K
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/validate.yml --ask-vault-pass -K
```

استقرار دارای توقف صریح برای مشاهده‌ی topology است و قبل از فعال کردن
HAProxy/Keepalived باید یک leader و دو standby در حالت streaming دیده شود.

## ساخت کاربر، رمز و دیتابیس

برای ساخت مدیریت‌شده از `playbooks/manage-postgresql-access.yml` و متغیرهای
`postgresql_managed_roles`، `postgresql_managed_databases`،
`postgresql_managed_memberships` و `postgresql_managed_access_profiles` استفاده
کنید. مثال کامل در [راهنمای ساخت کاربر و دیتابیس](راهنمای-ساخت-کاربر-و-دیتابیس.md)
است.

نمونه‌ی سطح دسترسی فقط‌خواندنی:

```yaml
postgresql_managed_roles:
  - name: reporting_owner
  - name: reporting_reader
    login: true
    password: "{{ vault_reporting_reader_password }}"
    password_version: v1
postgresql_managed_databases:
  - name: reporting
    owner: reporting_owner
postgresql_managed_access_profiles:
  - database: reporting
    schema: public
    owner: reporting_owner
    role: reporting_reader
    level: readonly
```

رمز هر برنامه را در Vault نگه دارید و مقدار آن را در فایل YAML معمولی ننویسید.
سطح `readonly` فقط حقوق مستقیم مدیریت‌شده را اصلاح می‌کند و در صورت باقی‌ماندن
حقوق ارثی یا owner، تراکنش را fail می‌کند.

## TLS و ترتیب فعال‌سازی

سه لایه مستقل وجود دارد: TLS PostgreSQL، HTTPS/mTLS برای REST Patroni و mTLS
برای client/peer etcd. هیچ‌کدام پیش‌فرض فعال نیستند و Ansible گواهی تولید
نمی‌کند. برای هر نود گواهی CA-signed با SANهای واقعی IP و DNS تهیه کنید.

برای کلاستر تازه، ابتدا sourceهای گواهی را در inventory تنظیم و با
`playbooks/deploy-postgresql-tls-certificates.yml` منتشر و اعتبارسنجی کنید؛ سپس
فعال‌سازی سرویس‌ها را انجام دهید. برای PostgreSQL ترتیب پیشنهادی این است:

1. انتشار و بررسی فایل‌ها؛
2. فعال کردن `postgresql_tls_activation_enabled` با حداقل TLS 1.2؛
3. آزمایش replication، rewind، VIP و اتصال برنامه؛
4. انتقال تدریجی `postgresql_tls_internal_sslmode` به `verify-full` پس از آماده
   بودن SANها؛
5. در پایان فعال کردن `postgresql_tls_require_ssl` و HBA مربوط.

برای etcd موجود، تغییر HTTP به HTTPS را rolling اجرا نکنید. از playbook هماهنگ
زیر در maintenance window استفاده کنید؛ playbook قبل از توقف سرویس snapshot
می‌گیرد و فقط پس از healthy شدن quorum marker می‌نویسد:

```bash
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/migrate-etcd-tls.yml --ask-vault-pass -K
```

این اجرا به `etcd_tls_enabled: true` و تأیید صریح
`etcd_tls_existing_cluster_migration_ack: true` نیاز دارد. برای کلاستر تازه
می‌توان TLS را از ابتدا روشن کرد، ولی source و SAN هر هفت فایل etcd باید موجود
باشد. برای Patroni REST حالت `none` یا `optional` استفاده می‌شود تا health check
HAProxy بدون کلید client کار کند؛ حالت `required` در این پیاده‌سازی رد می‌شود.

## شبکه و سخت‌سازی

ابتدا audit شبکه را اجرا کنید و source واقعی SSH/Ansible، برنامه و monitoring را
ثبت کنید. تا وقتی CIDRها بازبینی نشده‌اند enforcement را روشن نکنید:

```bash
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/audit-network-hardening.yml --ask-vault-pass -K
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/apply-network-hardening.yml --ask-vault-pass -K
```

`postgresql_admin_cidrs` باید شبکه مدیریت را محدود کند. از `0.0.0.0/0` برای SSH،
etcd یا metrics استفاده نکنید. قواعد مستقیم PostgreSQL را فقط در
`postgresql_hba_additional_rules` و پس از بررسی ثبت کنید.

## پشتیبان و بازیابی

مخزن pgBackRest باید خارج از سه نود، mountشده، writable و تحت بررسی باشد. برای
آماده‌سازی و راستی‌آزمایی:

```bash
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/configure-backups.yml --ask-vault-pass -K
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/verify-backups.yml --ask-vault-pass -K
```

قبل از پذیرش production، یک restore آزمایشی و بررسی WAL/PITR انجام دهید. تست
موفق backup به‌تنهایی ثابت نمی‌کند که بازیابی قابل استفاده است.

## پایش و عیب‌یابی

وضعیت سرویس‌ها، topology، endpointهای Patroni و etcd و metrics را بررسی کنید:

```bash
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/audit-postgresql-ha-monitoring.yml --ask-vault-pass -K
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/validate.yml --ask-vault-pass -K
```

اگر یک نود fail شد، ابتدا `patronictl list` و health etcd را از یک نود سالم
ببینید. برای restart یا patch از روش serial استفاده کنید و هیچ‌گاه دو عضو quorum
را هم‌زمان متوقف نکنید. برای node rebuild از playbook مربوط استفاده کنید و دیسک
نود جایگزین را قبل از join بررسی کنید.

## CI و مسیر GitHub به GitLab

workflow موجود GitHub روی Ubuntu 24.04، Python 3.12 و PostgreSQL 16 اجرا می‌شود،
syntax check و تست‌های regression/template را انجام می‌دهد و به کلاستر واقعی
دسترسی ندارد. قبل از merge باید تست‌ها و `git diff --check` سبز باشند.

برای انتقال بعدی به GitLab، همان مراحل را در `.gitlab-ci.yml` با Docker executor
بازسازی کنید: lint و unit test در مراحل خودکار، deploy فقط روی `prod`، و آخرین
مرحله با `when: manual` و approval محیط production. رمزهای CI را در GitLab
CI/CD Variables و گواهی/رمزهای حساس را از مسیر Vault یا artifact رمزگذاری‌شده
تأییدشده تحویل دهید؛ کلید خصوصی خام را در repository قرار ندهید.
