# راهنمای ساخت دیتابیس، کاربر و سطح دسترسی PostgreSQL

این پروژه ساخت حساب‌های PostgreSQL، دیتابیس‌ها، عضویت نقش‌ها و دسترسی‌های
رایج را به‌صورت declarative انجام می‌دهد. اجرای تغییرات فقط روی Leader فعلی
انجام می‌شود و بعد از آن اعتبارسنجی HA اجرا می‌شود.

## مدل پیشنهادی

برای هر سرویس چهار نقش جدا در نظر بگیرید:

| نقش | LOGIN | کاربرد |
|---|---:|---|
| `service_owner` | خیر | مالک دیتابیس و آبجکت‌ها؛ برای اتصال برنامه نیست |
| `service_rw` | خیر | سطح دسترسی خواندن/نوشتن |
| `service_ro` | خیر | سطح دسترسی فقط خواندن |
| `service_login` | بله | تنها نقش دارای رمز که برنامه با آن وصل می‌شود |

به این ترتیب تعویض رمز اتصال برنامه، مالکیت آبجکت‌ها و سیاست دسترسی را از هم
جدا می‌کند.

## نگهداری رمز

رمز نقش LOGIN را فقط در Ansible Vault قرار دهید. فایل رمزگشایی‌شده و کلید خصوصی
را commit نکنید.

```bash
ansible-vault edit inventory/production/group_vars/all/vault.yml
```

داخل Vault، برای نمونه، این متغیر را بسازید:

```yaml
vault_example_app_db_password: "یک-رمز-تصادفی-طولانی"
```

## نمونه تعریف

در `inventory/production/group_vars/all/main.yml` فقط آبجکت‌های تأییدشده را
اضافه کنید:

```yaml
postgresql_access_management_enabled: true

postgresql_managed_roles:
  - name: example_app_owner
    login: false
  - name: example_app_rw
    login: false
  - name: example_app_ro
    login: false
  - name: example_app_login
    login: true
    password: "{{ vault_example_app_db_password }}"
    password_version: "v1"
    connection_limit: 30

postgresql_managed_databases:
  - name: example_app
    owner: example_app_owner
    encoding: UTF8
    revoke_public_connect: true

postgresql_managed_memberships:
  - role: example_app_rw
    member: example_app_login
    admin_option: false

postgresql_managed_access_profiles:
  - database: example_app
    schema: public
    owner: example_app_owner
    role: example_app_rw
    level: readwrite
  - database: example_app
    schema: public
    owner: example_app_owner
    role: example_app_ro
    level: readonly
```

`owner` باید همان نقشی باشد که واقعاً آبجکت‌های آینده را ایجاد می‌کند؛ چون
`ALTER DEFAULT PRIVILEGES` فقط روی آبجکت‌های آینده‌ی همان creator اثر دارد.

## اعمال تغییرات

ابتدا dry-run و سپس اجرای واقعی را با بررسی diff انجام دهید:

```bash
ansible-playbook -i inventory/production/hosts.yml \
  playbooks/manage-postgresql-access.yml \
  --ask-vault-pass -K --check --diff

ansible-playbook -i inventory/production/hosts.yml \
  playbooks/manage-postgresql-access.yml \
  --ask-vault-pass -K
```

این role دیتابیس یا نقش را حذف نمی‌کند. حذف یا تغییر نام باید با فرایند جداگانه،
پس از بررسی وابستگی‌های برنامه، انجام شود.

## ساخت آبجکت و آزمایش اتصال

پس از ایجاد نقش‌ها، برنامه با نقش LOGIN وصل می‌شود؛ مالک یا نقش NOLOGIN نباید
برای اتصال برنامه استفاده شود. برای آزمایش، از یک محیط غیرتولیدی یا یک schema
آزمایشی استفاده کنید و این موارد را بررسی کنید:

```sql
SELECT current_user, current_database();
SELECT has_schema_privilege(current_user, 'public', 'USAGE');
```

برای نقش read-only باید `SELECT` موفق و `INSERT/UPDATE/DELETE` ناموفق باشد. برای
نقش read-write هر دو گروه عملیات باید طبق نیاز برنامه موفق باشد.

## چرخش رمز

1. رمز جدید را در Vault جایگزین کنید.
2. مقدار `password_version` را از `v1` به `v2` تغییر دهید.
3. ابتدا check mode و سپس playbook مدیریت دسترسی را اجرا کنید.
4. secret برنامه را هم‌زمان با یک rollout کنترل‌شده به‌روزرسانی کنید.
5. پس از تأیید اتصال، مقدار نسخه‌ی بعدی را برای تغییر بعدی نگه دارید.

خودکارسازی عمداً نقش‌ها و دیتابیس‌ها را drop نمی‌کند و تغییرات خارج از مدل
اعلام‌شده را به‌صورت مخرب بازنویسی نمی‌کند.
